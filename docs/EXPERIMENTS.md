# 实验记录

按时间顺序，包含失败的实验与工程事故。所有指标为主协议 K=2 的 balanced accuracy，
验证集为 fold 0（23,953 条，K=2 子集 10,926 条）。

---

## 硬件与耗时基准

单张 RTX 4060 Laptop（8GB）。实测吞吐：

| 配置 | 显存 | 步速 | 单轮耗时 |
|---|---|---|---|
| 512 tok, bs 32, 梯度检查点 | 2.3 GB | 1.74 s/step | 1.5 h（3,031 步） |
| 1024 tok, bs 16, 梯度检查点 | 2.3 GB | 2.5–3.6 s/step | 4.3 h（6,062 步） |
| 1024 tok, bs 64, 无检查点 | — | OOM（需 14.25 GB） | — |
| 1024 tok, bs 32, 无检查点 | 7.9/8.0 GB | 顶到上限，不可用 | — |

**结论：8GB 卡上必须开梯度检查点，bs 32（512 tok）/ bs 16（1024 tok）是最优点。**

## 逐项说明

### #1–2 基线与「密集子集」现象

全混合集上 TF-IDF 只有 0.6015，但在「≥7 个模型作答」的密集子集上有 0.8082。
差异来自后者几乎全是长文本。这说明**长度是主导变量**，早于任何模型改动的判断。

### #3–4 数据量实验

同一套代码：9,703 条 → 0.5684；96,993 条 → 0.8134。中间没有改任何超参。

### #6 1024 token：三次才拿到结果

* 第 1 次：跑一夜只到 800/6,062 步。原因不是睡眠，而是 Windows **新型待机（Modern Standby）**
  由「屏幕关闭」触发 —— 只把「睡眠」设为从不不够，必须把**关闭屏幕**也设为从不。
* 第 2 次：到达 6,000/6,062 步后卡死。因为脚本不存权重，5.5 小时全部丢失。
* 第 3 次：加上 `--save-every 500`，同样卡在 6,000 步，但这次用存档单独打分成功。

学习的率已退火到接近 0，因此 step 6000 的权重基本等同最终模型。

### #7 二元判别器

针对混淆最重的 8 个配对（kimi↔glm、gpt-5.6 sol↔luna、gemini 3.7↔3.8、
claude-opus-4-8↔fable-5、glm-5.3-flash↔glm-5.3）各训一个逻辑回归头，
只在 18 类预测落在该配对内时重判。

防泄漏设计：编码器训练时没见过 fold 0，再把 fold 0 按 prompt 拆成两半，
一半训二元头、一半评估。

改判 796/11,742 条（6.8%），净损失约 139 条正确预测。失败原因见 FINDINGS 第 3 节。

### #8–9 ArcFace 两次

第一次同时改了四样（损失、步数 3,600 vs 6,062、类别平衡采样、标签平滑），
无法归因。第二次做严格单变量：同起点、同 6,062 步、同 bs/lr、只保留类别权重、
无平滑、无采样、前 600 步冻结骨干。

结果更差（0.8021 vs 0.8330），说明**问题在损失函数本身，不在配置**。

### #10–11 集成

第 10 项之后发现一个反直觉现象：把 512-token 的旧模型加进来，
与 1024-token 的模型集成，效果比「CE + ArcFace」还好。
这直接引出第 11 项，并在 FINDINGS 第 4 节总结为「信息差异 > 方法差异」。

## 工程事故清单

| 现象 | 根因 | 处置 |
|---|---|---|
| 训练跑一夜只走 800 步，步速从 1.7s 恶化到 46s | Windows 新型待机（屏幕关闭触发），GPU 被电源门控 | `powercfg /change monitor-timeout-ac 0` |
| 进程存活、`nvidia-smi` 显示 99% 占用、日志不更新 | CUDA 上下文卡死（一次发生于 TDR 复位之后） | 杀进程；判断依据是 python 的 CPU 时间不增长 |
| 训练脚本末尾直接评估必卡 | 训练与推理同进程（三次复现） | 训练 `--no-eval`，评估独立进程 |
| 卡死后损失整轮训练 | 脚本不存权重 | `--save-every 500`，结束前无条件保存 |
| 后台任务长时间无输出 | stdout 被 `tail` 缓冲 | 重定向到文件后再 tail 文件 |
| 数据加载占用内存过高 | 压缩 npz 全量解压 | 转成 `.npy` 用 mmap |
